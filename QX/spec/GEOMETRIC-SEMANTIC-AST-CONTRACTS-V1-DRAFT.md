# مصفوفة العقود الدلالية والربط مع AST — QX V1 (مسودة)

**الحالة:** مسودة جرد وتصنيف؛ ليست اعتماداً دلالياً تنفيذياً.
**الفرع:** `audit/geometric-language-alignment`
**الأساس التركيبي المعتمد:** `GEOMETRIC-LANGUAGE-GRAMMAR-V1.md`
**مرجع الأشكال والأسماء والوظائف:** `الدستور الهندسي للغة QX — QX Geometric Language Specification.md`

## 1. الغرض وحدود هذه المسودة

تسجل هذه الوثيقة الرموز الـ72 المعتمدة، ووظيفتها الدستورية كما وردت دون توسيع، وتصنيفاً أولياً لدورها اللغوي بغرض تنظيم المراجعة. كما تفصل بين نوع العقدة النحوية الموجود حالياً وبين نوع العقدة الدلالية؛ وقد اعتمد المالك مبدئياً نموذج AST مشتركاً للمجموعة الأولى فقط، دون اعتماد عقودها الدلالية التنفيذية.

هذه المسودة **لا تعتمد** عدد الوسائط أو أنواعها أو نوع الناتج أو سياسة الكتل أو الأثر الجانبي أو صلاحيات التنفيذ لأي رمز. القيمة `UNSPECIFIED` تعني أن الدستور وقواعد V1 لا يقدمان عقداً كافياً لحسمها؛ ولا يجوز تحويلها إلى قيمة افتراضية في المحرك.

## 2. قواعد قراءة المصفوفة

- `GeometricStatement`: شكل AST النحوي الحالي عندما يظهر الرمز في موضع تعليمة.
- `GeometricCallExpression`: شكل AST النحوي الحالي عندما يظهر الرمز داخل تعبير.
- هذان النوعان لا يحسمان ما إذا كان الرمز دلالياً تعليمة أو تعبيراً؛ فذلك يظل قراراً خاصاً بعقد الرمز.
- `semanticNodeType`: اعتمد المالك مبدئياً الأنواع الستة المتخصصة للمجموعة الأولى تحت `DefinitionDeclaration` كما هو موثق في القسم 5.3. تبقى أنواع AST الدلالية لبقية الرموز غير محسومة (`UNSPECIFIED`). هذا الاعتماد المعماري لا يجيز تحويل الرمز إلى أمر تقليدي أو تنفيذ دلالته.
- `roleClass` تصنيف وصفي مستمد من الوظيفة الدستورية، وليس تصريحاً بأن الرمز قابل للتنفيذ أو صالح في أي سياق.
- قواعد V1 تسمح نحوياً بقائمة وسائط فارغة أو غير فارغة وبكتلة اختيارية عامة؛ أما قبولها فعلياً فيحدده العقد الدلالي الخاص بالرمز.
- `⧯ FINISH` يعني إنهاء عملية وفق الدستور، ولا يمثل إغلاق كتلة؛ إغلاق الكتل حصراً بواسطة `}`.

## 4. حقول العقد الدلالي لكل رمز

يجب أن يحتوي كل عقد نهائي على الحقول التالية. الحالة الحالية لكل الحقول غير المحسومة هي `UNSPECIFIED`، ولا يجوز للمحلل أو المترجم استنتاجها من `roleClass` أو اسم المجموعة.

| الحقل | الحالة الحالية | شرط الحسم |
|---|---|---|
| glyph | مثبت في الدستور والسجل | تطابق حرفي مع Unicode المعتمد |
| name | مثبت دستورياً | الاسم الداخلي `ELSE_IF` يقابل دستورياً `ELSE-IF` دون تغيير الاسم الدستوري |
| group | مثبت في السجل | تطابق المجموعة الدستورية |
| role | مثبت بالوصف الدستوري فقط | لا يضاف سلوك خارج الوظيفة المعلنة |
| astNodeType | معتمد مبدئياً للمجموعة الأولى فقط وفق القسم 5.3؛ وبقية الرموز `UNSPECIFIED` | لا يُستنتج أي عقد إضافي أو سلوك تنفيذي من اسم النوع |
| argumentSchema | UNSPECIFIED | تحديد العدد، الإلزامية، الترتيب، والقيم الاختيارية لكل رمز |
| inputTypes | UNSPECIFIED | تحديد أنواع كل وسيط وقواعد التوافق |
| outputType | UNSPECIFIED | تحديد هل ينتج قيمة، ونوعها، أو لا ينتج قيمة |

| executionCategory | تصنيف وصفي فقط | تحديد ما إذا كان Pure / Stateful / I/O / Control / Build / Host-capability وغيرها، مع صلاحياته |

## 5. عقد AST الحالي مقابل AST الدلالي المستهدف

### 5.1 الموجود حالياً

ينتج Parser حالياً شكلين نحويين عامين:

```text
GeometricStatement {
  symbol, glyph, group, args, body, alternate, location
}

GeometricCallExpression {
  symbol, glyph, group, args, location
}
```

هذه العقد تحفظ الرمز ومعلومات المصدر، لكنها لا تصف بعد نوعاً أو معنى دلالياً خاصاً بالرمز. كما أن Parser يسمح حالياً نحوياً بكتلة بعد أي رمز، وبقائمة وسائط فارغة؛ وهذا لا يعني أن كل رمز يقبل ذلك دلالياً.

### 5.2 النموذج المستهدف المقترح للمراجعة

يُفضل الحفاظ على عقدة استدعاء هندسي موحدة تحمل هوية الرمز والموقع، ثم إضافة تمثيل دلالي متخصص بعد التحقق من العقد. أسماء الأنواع الستة للمجموعة الأولى معتمدة مبدئياً وفق قرار المالك؛ ولا يعني ذلك اعتماد توقيعاتها أو سلوكها أو توقيت إنشائها. يظل `GeometricInvocation` أدناه نموذجاً مفاهيمياً غير منفذ، ولا يحل محل العقد الحالية أو قرار المجموعة الأولى.

```text
GeometricInvocation (conceptual, not implemented)
  symbolId
  glyph
  canonicalName
  group
  arguments
  body
  alternate
  sourceLocation
  resolvedContract
  semanticResult
```

هذا نموذج مفاهيمي للنقاش فقط، وليس تغييراً معتمداً على AST أو API عامة. يجب أن يظل AST الخام قابلاً للفحص حتى عند فشل التحليل الدلالي.


### 5.3 النموذج المشترك المعتمد مبدئياً للمجموعة الأولى

**قرار المالك — 2026-11-28:** اعتماد مبدئي لنموذج AST مشترك باسم `DefinitionDeclaration`، وتكون الرموز الستة التالية أنواعاً متخصصة تحته:

| الرمز | الاسم الدستوري | نوع AST |
|---|---|---|
| ⬡ | ORIGIN | `OriginDeclaration` |
| ⬢ | FORM | `FormDefinition` |
| ◈ | CORE | `CoreEntityDeclaration` |
| ⬣ | SEED | `ComponentDeclaration` |
| ⬠ | ROOT | `RootSelectionDeclaration` |
| ⟐ | IDENTITY | `IdentityDeclaration` |

حدود هذا الاعتماد:

1. يحتفظ كل نوع بهوية الرمز وشكله واسمه الدستوري ووظيفته الأصلية دون تغيير.
2. الاعتماد معماري مبدئي لأسماء الأنواع وعلاقة التخصص فقط؛ وليس اعتماداً لدلالات أو وظائف إضافية.
3. لا يحدد هذا القرار عدد الوسائط أو أنواعها أو مخرجاتها أو سياسة الكتل أو سياقات الاستخدام.
4. لا يفرض علاقات إلزامية بين الأنواع أو ترتيباً بينها.
5. لا يحدد متى يحدث التعريف أو التسجيل أو الإنشاء الفعلي أو الإتاحة للاستخدام.
6. لا يحسم تعديل التعريفات أو معالجة التكرار والتعارض.
7. تبقى جميع الحقول غير المحسومة `UNSPECIFIED` ولا تتحول إلى قيم افتراضية.
8. لا يستبدل هذا النموذج عقدتي Parser الحاليتين `GeometricStatement` و`GeometricCallExpression`؛ وطريقة التكامل معهما ومع المحرك التقليدي ما زالت قيد الدراسة.
9. عند صدور هذا القرار كان اعتماد AST وحده لا يمنح إذناً بتعديل ملفات المصدر أو إضافة قواعد Semantic Analyzer أو QIR. صدر لاحقاً التكليف الهندسي الشامل بتاريخ 2026-11-28، وهو يفوض التنفيذ ضمن العقود المعتمدة وحدود `UNSPECIFIED` الواردة هنا.

### 5.5 قرار مواضع استخدام المجموعة الثانية

**قرار هندسي معتمد — 2026-11-28:** تثبيت مواضع الاستخدام التالية للمجموعة الثانية فقط:

| الرمز | الاسم | موضع الاستخدام |
|---|---|---|
| ◉ | DATA | `STATEMENT_ONLY` |
| ◍ | STORE | `STATEMENT_ONLY` |
| ◌ | FETCH | `EXPRESSION_ONLY` |
| ⊙ | VALUE | `STATEMENT_ONLY` |
| ⊚ | RECORD | `STATEMENT_ONLY` |
| ⊛ | COLLECTION | `STATEMENT_ONLY` |

التعليل: التعريف والتخزين وتحديد القيمة وإنشاء السجل والمجموعة تعامل كتعليمات؛ أما FETCH فيعامل كتعبير لأنه يمثل جلب قيمة قابلة للاستخدام داخل تعبير.

حدود القرار:
1. يحدد هذا القرار موضع الاستخدام فقط.
2. لا يحدد عدد الوسائط أو أنواعها أو مخططها.
3. لا يحدد نوع المخرج أو علاقته بنموذج البيانات.
4. لا يحدد سياسة الكتل أو النطاق أو الصلاحيات أو الآثار الجانبية التفصيلية.
5. لا يمنح الرموز دلالات تنفيذية مكتملة؛ تظل العقود الأخرى `UNSPECIFIED` ويظل خفضها إلى QIR محجوباً.
6. يرفض Semantic Analyzer موضع الاستخدام المخالف، ويستمر في رفض الموضع الصحيح أيضاً إلى حين اعتماد بقية العقد الدلالي.

### 5.4 تنفيذ جسر AST للمجموعة الأولى

أضيفت وحدة `geometric-ast-adapter.js` بوصفها طبقة تحويل غير مدمرة بين AST النحوي والأنواع المعمارية المعتمدة للمجموعة الأولى:

- يحوّل فقط عقد `GeometricStatement` للرموز الستة المعتمدة إلى أنواعها المتخصصة.
- يضع `parentType: DefinitionDeclaration` و`syntaxType: GeometricStatement` لتثبيت علاقة النوع مع الاحتفاظ بأصل العقدة النحوية.
- يحافظ على `symbol` و`glyph` و`group` و`args` و`body` و`alternate` و`location` دون تفسير أو تغيير.
- التحويل عميق وغير مدمّر؛ يبقى AST الأصلي الذي ينتجه Parser كما هو.
- لا يحوّل `GeometricCallExpression` ولا أي رمز من المجموعات الأخرى؛ تبقى عقودها غير محسومة.

### 5.8 العقود الدلالية المختارة للمجموعة الثانية — سجل القرار الأولي 2026-11-28 (حالة RECORD مستبدلة بالقسم 5.13)

**الحالة:** اختار المساعد هذا التصميم بناءً على تفويض المالك الصريح «اعمل الأفضل انت ختار». تم تسجيله كقرار عقدي، وليس كادعاء بأن التنفيذ أو QIR أصبح جاهزاً.

#### المبادئ العامة

1. التمييز بين تعريف ربط قابل للتعديل وتعريف ربط ثابت: `DATA` قابل للتعديل، و`VALUE` غير قابل لإعادة الإسناد.
2. `STORE` لا ينشئ اسماً جديداً؛ بل يحدّث ربطاً موجوداً وقابلاً للتعديل فقط.
3. `FETCH` قراءة تعبيرية لربط موجود ومهيأ، ويعيد نوعه الثابت دون تحويل ضمني.
4. `COLLECTION` تنشئ قائمة فارغة من نوع `LIST`، متوافقة مع نظام القوائم الموجود في QX V1.
5. لا تُختزل السجلات إلى قوائم. `RECORD` يحتاج نوعاً وتمثيلاً صريحين غير موجودين في QX V1، ولذلك يظل مؤجلاً ومحجوباً.
6. النطاق: التعريف على مستوى الوحدة ينشئ ربطاً عاماً، والتعريف داخل الدالة ينشئ ربطاً محلياً. يُحافظ على قاعدة QX V1 التي تمنع حجب اسم الوحدة بتعريف محلي داخل الدالة.
7. جميع الرموز الستة ممنوعة من قبول كتل؛ `allowsBody = FORBIDDEN`.
8. اعتماد هذه العقود لا يجيز QIR lowering أو VM/backend قبل تنفيذ الحراس الدلالية والتحويلات والاختبارات الخاصة بكل رمز.

#### قواعد النطاق والتعديل

- تُرفض الأسماء المكررة في النطاق نفسه، ويُمنع تعريف اسم محلي يحجب اسماً على مستوى الوحدة، اتساقاً مع قواعد QX V1 الحالية.

- داخل الدالة، يسمح `STORE` بتحديث ربط محلي تابع للدالة فقط. تحديث ربط الوحدة من داخل دالة ممنوع في هذا العقد؛ لا توجد هنا صيغة هندسية مستقلة لتفويض تعديل global من الدالة.
