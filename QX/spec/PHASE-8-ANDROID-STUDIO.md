# المرحلة الثامنة — QX Studio على Android

**الحالة:** مواصفة تأسيسية أولية؛ التنفيذ البرمجي لم يبدأ.  
**الفرع الأولي:** `phase8/android-studio-spec`  
**المرجع:** `QX/spec/ROADMAP-EXECUTION-DECISION.md` و`QX/README.md`.

## 1. الهدف

إنشاء تطبيق Android باسم QX Studio يوفّر بيئة عملية لإدارة مشاريع QX، ومراجعة مخطط المشروع واعتماده، والعمل على الملفات، وتشغيل مسارات البناء والاختبار والمعاينة والتسليم التي تدعمها نواة QX.

هذه المرحلة تنقل قدرات QX المعتمدة إلى بيئة Android؛ ولا تختزل هدف QX إلى محرر أكواد أو تطبيق Android محدود. تبقى اللغة والمحرك ومكتبة المكونات وواجهات المشاريع الحالية أساساً مستقلاً قابلاً لإعادة الاستخدام.

## 2. قرار معماري أولي قابل للمراجعة

اعتمد المستخدم هذا الاتجاه بوصفه **خط أساس قابلاً للتعديل لاحقاً**. لا يُعد اختيار التقنيات أدناه قراراً غير قابل للرجوع، ولا يسمح بتغيير محرك QX أو عقوده من دون موافقة مستقلة.

1. **طبقة تطبيق Android أصلية:** Kotlin لإدارة دورة حياة التطبيق، والتنقل، والأذونات، والتكامل مع نظام Android.
2. **طبقة Studio:** واجهة لإدارة المشاريع والملفات والمخططات والموافقات والاختبارات والمعاينة والتسليم.
3. **طبقة تشغيل QX:** تقييم إمكانية تشغيل أجزاء JavaScript المتوافقة داخل WebView، عبر واجهة تكامل محددة ومعزولة. لا يُفترض أن نواة QX الحالية تعمل كاملة داخل WebView كما هي.
4. **جسر Android محدود:** واجهات صريحة ومحددة الصلاحيات بين JavaScript وKotlin، دون كشف واجهات النظام العامة إلى محتوى WebView.
5. **طبقة تخزين Android:** واجهة تخزين مستقلة خلف عقد واضح، مع دراسة Storage Access Framework ومزوّدات الملفات التي يختارها المستخدم. لا تُفترض صلاحية الوصول الشامل إلى ملفات الجهاز.
6. **فصل المنصات:** إبقاء منطق QX العام مستقلاً عن Android، وعزل أي تنفيذ خاص بالمنصة خلف adapters/interfaces.

### 2.1 قابلية تعديل القرار

- تُسجّل القرارات التقنية الجوهرية في سجل قرارات معماري (ADR) مع البدائل والأسباب والآثار.
- يجوز اقتراح استبدال WebView أو تعديل حدود Kotlin/JavaScript أو تغيير استراتيجية التخزين إذا أثبتت الاختبارات أو متطلبات المنتج حاجة لذلك.
- أي تعديل معماري لاحق يمر بمراجعة توافق وأمان واختبارات ترحيل، ولا يُنفذ لمجرد أنه ممكن تقنياً.
- لا تُكسر واجهات QX العامة أو صيغة المشاريع المعتمدة دون قرار منفصل وخطة توافق.
- لا يُحذف أو يُنقل أو يُستبدل أي ملف أو مكوّن قائم دون تفويض صريح.

## 3. فحص التوافق قبل التنفيذ

تحتوي نواة `engine/qx-core` على JavaScript ES Modules، بينما تعتمد بعض وحدات إدارة المشاريع الحالية على واجهات Node.js مثل `node:fs/promises` و`node:path` و`node:crypto`. لذلك:

- يجب إعداد خريطة اعتماديات فعلية لكل وحدة مطلوبة في Android.
- تُصنف الوحدات إلى: قابلة للتشغيل مباشرة، قابلة للتشغيل بعد adapter، أو غير متوافقة حالياً.
- لا تُستورد وحدات Node المعتمدة على نظام الملفات مباشرة في WebView.
- تُستبدل تبعيات المضيف فقط عبر عقود adapters معتمدة، ولا تُغيّر دلالات المحرك.
- يجب تحديد بديل متوافق للتشفير والبصمات والملفات قبل اعتماد أي تنفيذ؛ مع اختبارات تثبت تطابق النتائج حيث يلزم.
- لا يُعلن دعم ميزة في Android قبل اختبارها على بيئة Android فعلية أو محاكي مناسب.

## 4. نطاق المنتج

### 4.1 إدارة المشاريع
- إنشاء مشروع وفتحه وإعادة فتحه من مساحة يحددها المستخدم.
- عرض المشاريع الحديثة ومعلوماتها وحالتها.
- إنشاء مساحة مشروع دون المساس بمجلدات أخرى.
- التعامل مع فشل الوصول أو سحب الإذن أو حذف/نقل الملف من خارج التطبيق برسائل واضحة.

### 4.2 المخطط والموافقة
- عرض manifest والمتطلبات والصفحات والبيانات والتكاملات والأسئلة المفتوحة.
- إظهار الفروقات بين المراجعات.
- طلب موافقة صريحة على بصمة المخطط المحددة قبل البناء.
- إبطال الموافقة عند تعديل المخطط وفق عقد المرحلة السابعة.

### 4.3 الملفات والتحرير
- عرض شجرة ملفات المشروع وفتح الملفات المدعومة.
- حفظ التعديلات ضمن مساحة العمل المصرح بها فقط.
- إظهار الملفات المعدلة وحالة الحفظ والتعارضات.
- عدم الكتابة أو الاستبدال أو الحذف خارج نطاق تفويض واضح.

### 4.4 البناء والاختبار
- استدعاء مسارات QX المتاحة عبر طبقة تكامل واضحة.
- عرض مراحل البناء وحالاتها والأخطاء المرتبطة بالملف أو المهمة عند توفرها.
- عرض نتائج component وcontract وintegration وproject وuser_flow، مع التمييز بين passed/failed/skipped/not_run.
- عدم اعتبار الاختبارات غير المنفذة ناجحة.

### 4.5 المعاينة والتسليم
- معاينة نواتج Web Backend ضمن بيئة معزولة.
- عدم تمكين الوصول للشبكة أو الملفات أو واجهات المضيف افتراضياً داخل محتوى المعاينة.
- عرض تقرير التسليم والملفات والبصمات والاختبارات والمشكلات المفتوحة.
- لا نشر أو رفع خارجي أو مشاركة تلقائية ضمن هذه المرحلة دون موافقة ونطاق منفصلين.

## 5. الأمان والخصوصية

- مبدأ أقل صلاحية في كل من Kotlin وJavaScript وجسر WebView.
- تقييد WebView إلى المحتوى المحلي الموثوق الذي ينشئه التطبيق، ومنع الوصول غير الضروري إلى الشبكة والملفات والواجهات الحساسة.
- التحقق من كل رسالة تعبر الجسر: نوع العملية، المدخلات، حجم البيانات، صلاحية المشروع، والإذن الحالي.
- لا تُمرر أسرار أو رموز وصول إلى JavaScript أو سجلات التشخيص.
- طلب صلاحيات الملفات عند الحاجة فقط، مع احترام اختيار المستخدم وإمكانية إلغاء الإذن.
- لا تُنفذ أوامر shell أو كود مضيف غير موثوق.
- سجل عمليات قابل للمراجعة، دون تسجيل محتويات حساسة افتراضياً.

## 6. خطة الشرائح المقترحة

### 8.1 تأسيس التطبيق وعقد المنصّة
هيكل Android أولي، إعداد البناء، دورة حياة التطبيق، تعريف حدود الوحدات وواجهات adapters، وتوثيق ADR الأولي. لا ربط كامل بالمحرك في هذه الشريحة.

### 8.2 طبقة التخزين ومساحات العمل
واجهة تخزين موحدة، اختيار مجلد/مستند من المستخدم، إدارة الإذن، وعمليات قراءة/كتابة محدودة. اختبارات منع الوصول غير المصرح به وسحب الإذن.

### 8.3 تشغيل نواة QX والتوافق
خريطة اعتماديات وحدات QX، تشغيل أصغر مسار متوافق، وتوثيق الوحدات التي تحتاج adapters أو تبقى غير مدعومة. لا تغيير لعقد QX لمجرد تسهيل النقل.

### 8.4 واجهة Studio وإدارة المشاريع
قائمة المشاريع، فتح/إنشاء مشروع، شجرة الملفات، عرض manifest والمراجعات، وحالة العمل.

### 8.5 جسر Android/JavaScript
قناة رسائل محدودة ومتحقق منها، ربط العمليات المصرح بها، واختبارات صلاحيات وحدود وأحجام ورسائل غير صالحة.

### 8.6 البناء والاختبار
تشغيل workflow المشروع عبر واجهات Android، عرض التقدم والتقارير والأخطاء، والتحقق من عدم تجاوز مساحة العمل.

### 8.7 المعاينة والتسليم
معاينة ناتج Web، عرض تقرير التسليم، وتصدير محلي إلى وجهة يختارها المستخدم بعد تأكيد واضح.

### 8.8 التوافق والاستقرار والإصدار
اختبارات على إصدارات Android والأحجام/الاتجاهات المدعومة، دورة الحياة والاستعادة، الأداء الأساسي، وإغلاق الثغرات قبل اعتبار المرحلة مكتملة.

## 7. بوابة القبول النهائية

لا تُغلق المرحلة الثامنة قبل إثبات ما يلي:

1. بناء تطبيق Android قابل للتثبيت والتشغيل وفق الحد الأدنى لإصدارات Android الذي سيُعتمد في شريحة 8.1.
2. إنشاء مشروع تجريبي وفتحه وإعادة فتحه دون فقد البيانات.
3. اختيار مساحة تخزين عبر آلية Android المعتمدة، واحترام الإذن بعد منحه أو سحبه.
4. عرض manifest ومراجعاته وفرض الموافقة على البصمة قبل أي بناء أو كتابة.
5. تشغيل مسار QX تجريبي مثبت التوافق، مع توثيق الوحدات غير المدعومة بدلاً من الادعاء بتوافق كامل.
6. إثبات أن جسر Android لا يسمح بعمليات غير معرفة أو غير مصرح بها، وأن محتوى المعاينة لا يحصل على صلاحيات المضيف.
7. تنفيذ بناء واختبارات على مشروع تجريبي، وعرض حالات الفشل والاختبارات غير المنفذة بصدق.
8. معاينة الناتج وإنشاء تقرير تسليم وتصديره فقط إلى وجهة يختارها المستخدم.
9. اجتياز اختبارات الوحدة والتكامل والاختبارات على Android/محاكي، إضافة إلى فحوص CI.
10. عدم إدخال تغييرات غير معتمدة على نواة QX أو ملفات المشاريع القائمة.

## 9. قرارات مؤجلة لا يجوز افتراضها

تُحسم كل نقطة في الشريحة المرتبطة بها، بعد عرض البدائل والأثر:

- الحد الأدنى لإصدار Android ونسخ الأجهزة المستهدفة.
- اعتماد WebView نهائياً أو اختيار runtime بديل بعد قياس التوافق.
- مكتبة واجهة Android وأسلوب التصميم.
- استراتيجية التخزين الدائم والمزامنة والنسخ الاحتياطي.
- الوحدات المحددة من نواة QX التي ستعمل داخل Android، وما يحتاج إلى adapters.
- سياسة تصدير الحزم، والامتدادات المدعومة، وحدود أحجام الملفات.
- دعم العمل دون اتصال ومتطلبات الشبكة المستقبلية.
- التوقيع والتوزيع وقنوات النشر؛ لا تدخل ضمن التنفيذ قبل قرار مستقل.

## 10. حدود هذه المواصفة

هذه الوثيقة تثبت اتجاهاً معمارياً أولياً ونطاقاً ومصفوفة قبول. لا تثبت وجود تطبيق Android أو نجاح تشغيل QX داخله. ولا تعني أن WebView أو Storage Access Framework قد اختُبرا أو اعتُمدا نهائياً. يبدأ التنفيذ فقط عبر شرائح صغيرة، مع اختبار كل شريحة ومراجعة أثرها قبل الانتقال إلى التالية.
