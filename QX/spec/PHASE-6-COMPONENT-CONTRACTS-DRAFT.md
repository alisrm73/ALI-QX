# المرحلة السادسة — عقود مكتبة QX وخطة التنفيذ

> الحالة: **المرحلة السادسة قيد التنفيذ؛ مجموعة DATA منفذة على PR #6 واجتازت 109 اختباراً، ولم تُغلق المرحلة كاملة بعد.**  
> فرع التنفيذ: `feature/phase6-data-ops`  
> طلب المراجعة: https://github.com/alisrm73/ALI-QX/pull/6  
> الأساس: `main` بعد دمج المرحلة الخامسة.

## 1. الهدف والحدود

تحدد المرحلة السادسة عقود مكتبة QX القابلة لإعادة الاستخدام ضمن المجموعات الأربع المعتمدة حصراً:

- `DATA` — البيانات.
- `UI` — الواجهات.
- `PROCESS` — المعالجة.
- `INTEGRATION` — التكامل.

المجال `QX` مجال نظامي مستقل لأوامر دورة حياة أداة QX، وليس مجموعة مكتبة خامسة.

الهدف من هذه المرحلة هو توثيق هوية كل أمر أو مكوّن، اسمه العربي والإنجليزي، مدخلاته ومخرجاته وأنواعه، اعتماديته، صلاحياته، إصداره، وأدلة اختباره. لا يُعد إدراج الاسم في السجل موافقة على تنفيذه.

## 2. قواعد لا يجوز كسرها

1. تبقى مواصفة QIR V1.0 ثابتة؛ أي توسعة تتم بمواصفة إصدار مستقل متوافق مثل QIR 1.1، دون تغيير دلالات V1.0.
2. لا يُفعّل أي أمر قبل اكتمال عقده واعتماد العقد، ثم تنفيذ مسار التحليل والتنفيذ والاختبار اللازم له.
3. لا يُدّعى دعم واجهة أو تكامل خارجي لمجرد تسجيل اسمه.
4. لا تنفذ بيئة VM أو Web Backend عمليات شبكة أو ملفات مضيف أو شيفرة ديناميكية عبر مسار غير مصرح به.
5. أي تكامل خارجي يمر عبر موصل معتمد وصلاحيات محددة؛ لا تُخزّن مفاتيح الوصول أو الأسرار داخل ملفات QX أو مخرجات الويب.
6. تُستخدم أقل صلاحية لازمة، ويكون المنع هو الوضع الافتراضي عند غياب تصريح واضح.
7. إصدارات المكونات مثبتة لكل مشروع؛ لا يُحدّث مشروع قائم تلقائياً إلى إصدار أحدث.
8. لا يُعدّل إصدار مشترك مستخدم دون تحليل أثر وموافقة صريحة؛ يمكن إصدار نسخة جديدة بدلاً منه.
9. تُختبر المكونات منفردة، ثم توافقها مع المكتبة، ثم استخدامها في مشروع فعلي.
10. لا حذف ولا استبدال ولا نقل لأي ملف أو مكوّن قائم ضمن هذه المرحلة دون إذن صريح مستقل.

## 3. قالب العقد الموحد

يجب أن يتضمن كل عقد، بحسب طبيعة العنصر:

| الحقل | المطلوب |
|---|---|
| المعرّف | معرّف ثابت بصيغة DOMAIN.NAME |
| الاسم | اسم إنجليزي واحد واسم عربي واحد مرتبطان بالمعرّف نفسه |
| النوع | أمر لغة، مكوّن واجهة، معالج بيانات، أو موصل تكامل |
| الإصدار | إصدار مستقل وسياسة توافق واضحة |
| الوصف | وظيفة واحدة محددة وحدود ما لا يفعله العنصر |
| المدخلات | الاسم، النوع، الإلزام، القيمة الافتراضية، القيود والتحقق |
| المخرجات | النوع، شكل القيمة أو مرجع المكوّن، أو التصريح بأنه لا توجد قيمة |
| الأثر | نقيّ/حتمي، أو يغيّر حالة، أو ينفذ أثراً خارجياً |
| الاعتماديات | المكونات والخدمات والإصدارات المطلوبة |
| الصلاحيات | القدرات المطلوبة ومتى تُطلب وكيف تُرفض |
| الأخطاء | رموز ثابتة، أسبابها، وموضع المصدر عند توفره |
| الحدود | حدود الحجم والوقت والموارد والسلوك عند تجاوزها |
| التوافق | التغييرات المتوافقة وغير المتوافقة وسياسة الترقية |
| الاختبارات | وحدات، حالات رفض، تكامل، انحدار، وأمن بحسب نوع العنصر |

لا يجوز ترك نوع المدخل أو المخرج غامضاً. ولا يجوز استنتاج التوقيع من مثال استخدام قديم أو اسم أمر فقط.

## 4. سجل الأوامر الحالي

الأسماء التالية موجودة فعلياً في سجل QX الحالي. وجودها لا يعني أن عقودها مكتملة.

### DATA

| الأمر | الاسم العربي المسجل | حالة العقد الحالية | ملاحظة |
|---|---|---|---|
| `DATA.CREATE` | إنشاء | يحتاج عقد مكتبة موحداً | له معالجة خاصة في Semantic Analyzer، وليس أمراً مفعّلاً في Registry |
| `DATA.SET` | تعيين | غير معتمد التنفيذ كأمر مستقل | له معالجة خاصة في Semantic Analyzer |
| `DATA.SET_GLOBAL` | تعيين_عام | غير معتمد التنفيذ كأمر مستقل | له معالجة خاصة في Semantic Analyzer |
| `DATA.ADD` | إضافة | منفذ في PR #6 | تعبير LIST جديد؛ إضافة إلى نهاية القائمة؛ نسخ عميق |
| `DATA.REMOVE` | إزالة | منفذ في PR #6 | تعبير LIST جديد؛ حذف حسب فهرس صفري؛ نسخ عميق |
| `DATA.GET` | جلب | معلق | لا توقيع معتمداً |
| `DATA.COUNT` | عدد | عقد دلالي محدد ومفعّل | مدخل LIST واحد، ومخرج NUM |

### UI

| الأمر | الاسم العربي المسجل | حالة العقد الحالية | ملاحظة |
|---|---|---|---|
| `UI.SHOW` | عرض | معلق | لا توقيع أو تنفيذ واجهة معتمد |
| `UI.TEXT` | نص | معلق | لا توقيع أو تنفيذ واجهة معتمد |

أسماء مكونات الواجهة الأخرى الواردة في الوثائق العامة مثل PAGE وBUTTON وIMAGE وFIELD وBOX وCARD وROW وCOL وغيرها تبقى مقترحات غير معتمدة، ولا تُضاف إلى السجل في هذه الخطوة.

### PROCESS

| الأمر | الاسم العربي المسجل | حالة العقد الحالية | ملاحظة |
|---|---|---|---|
| `PROCESS.ADD` | إضافة | معلق | الاسم وحده لا يحدد العملية أو توقيعها |
| `PROCESS.CALCULATE` | احسب | عقد دلالي محدد ومفعّل | يخزن نتيجة NUM في متغير NUM معلن |
| `PROCESS.COMPARE` | قارن | عقد دلالي محدد ومفعّل | يخزن نتيجة BOOL في متغير BOOL معلن |

الأسماء التاريخية مثل MATH وWAIT وTIMER وDATE وRANDOM وFORMAT وVALIDATE وERROR ليست أوامر معتمدة.

### INTEGRATION

| الأمر | الاسم العربي المسجل | حالة العقد الحالية | ملاحظة |
|---|---|---|---|
| `INTEGRATION.REQUEST` | طلب | معلق | لا اتصال خارجي أو موصل أو صلاحيات معتمدة |

الأسماء CONNECT وSEND وRECEIVE وFILE وIMPORT وEXPORT مقترحات تاريخية غير معتمدة، ولا تصبح أوامر بمجرد ورودها في قائمة.

## 5. متطلبات خاصة بكل مجموعة

### 5.1 DATA

يجب أن يحدد كل عقد بوضوح:
- هل العملية تنشئ قيمة أو تقرؤها أو تعدلها أو تحذف عنصراً من قائمة؟
- هل المدخل LIST أم اسم متغير أم فهرس أم قيمة؟ وما أنواع كل وسيط؟
- هل العملية تعيد قيمة أم تعدل متغيراً معلناً أم الاثنين؟
- قواعد حدود الفهارس والقيم غير الموجودة والقوائم الفارغة.
- هل التعديل محلي أم عام، وكيف ينعكس على نطاق المتغيرات؟
- سلوك النسخ والتعديل للقوائم، وحدود طولها.

`DATA.ADD` و`DATA.REMOVE` لهما عقدان منفذان وموثقان في `PHASE-6-DATA-CONTRACTS-DRAFT.md`، مع امتداد QIR 1.1 مستقل. `DATA.GET` مؤجل من V1 بسبب غياب نوع آمن لعناصر القوائم المختلطة.

### 5.2 UI

يجب أن يحدد عقد كل مكوّن:
- نوع المكوّن ومعرّفه الفريد وعلاقته بالشجرة الأب/الابن.
- الخصائص وأنواعها وقيمها الافتراضية وحدودها.
- المحتوى أو العناصر الأبناء المسموح بها.
- قواعد التنسيق والتخطيط والاستجابة للشاشات.
- حالات التفاعل والأحداث ومخرجاتها وأنواع بياناتها.
- إمكانية الوصول، النصوص البديلة، وتسميات عناصر التحكم.
- قواعد إظهار المكوّن وإخفائه وتحديثه، دون حذف غير مقصود.
- طريقة تمثيله في QIR أو في طبقة بناء الويب، بعد اعتماد تصميم تقني منفصل.

**قيد تقني قائم:** QIR V1 لا يعرّف تعليمات UI، وWeb Backend الحالي لا ينفذ UI.TEXT أو UI.SHOW. لذلك لا يمكن إعلان تنفيذ مكونات UI في المرحلة السادسة دون مواصفة امتداد مستقلة ومتوافقة واختبارات لها. لا يُعدّل QIR V1 في هذه المسودة.

### 5.3 PROCESS

يجب أن يحدد العقد:
- هل هو تحويل قيمة نقي، أم عملية تغيّر حالة، أم عملية ذات أثر جانبي؟
- أنواع المدخلات والمخرجات وقواعد التحويل والتقريب.
- التوقيت والانتظار والمهل إن وجدت، وحدود التنفيذ.
- الحتمية ومصدر العشوائية إن اعتمدت عملية عشوائية مستقبلاً.
- طريقة الإبلاغ عن أخطاء التحقق والمعالجة.
- هل يمكن استخدامه كتعبير يعيد قيمة أم كتعليمة مستقلة فقط؟

لا تُعتمد أسماء أوامر جديدة ولا تُستنتج وظائفها من الاسم.

### 5.4 INTEGRATION

يجب أن يحدد عقد كل موصل:
- الخدمة أو النظام المستهدف وإصداره ونطاق الدعم.
- البروتوكول والوجهة المسموح بها، دون فتح اتصال عام افتراضياً.
- أنواع الطلبات والبيانات ومخططات التحقق منها.
- آلية المصادقة ومصدر الأسرار الآمن، دون تضمينها في المصدر أو ملفات النشر.
- الصلاحيات التي يوافق عليها المستخدم ونطاقها ومدة صلاحيتها.
- مهلة الاتصال، حدود الحجم، وسياسة إعادة المحاولة ومعدل الطلبات.
- تصنيف الأخطاء، التعامل مع انقطاع الخدمة، وتسجيل العمليات دون كشف الأسرار.
- منع الوصول إلى وجهات غير مصرح بها، ومنع تسريب البيانات بين المشاريع.

**قيد تقني قائم:** VM وWeb Backend الحاليان لا يقدمان واجهة شبكة أو موصلات خارجية. يجب تصميم طبقة موصلات معزولة ومصرح بها قبل تنفيذ أي طلب خارجي.

## 6. الإصدارات والاعتماديات

- لكل مكوّن أو موصل رقم إصدار مستقل.
- يثبت المشروع إصدار كل اعتماد يستخدمه؛ لا توجد ترقية تلقائية.
- توثق كل نسخة التغييرات والاعتماديات ونتائج الاختبارات.
- لا يكفي تطابق رقم الإصدار لإثبات التوافق؛ يجب تحديد نطاق التوافق واختباره.
- أي تغيير يكسر العقد يتطلب إصداراً رئيسياً جديداً وخطة ترحيل واضحة.
- تحتفظ المكتبة بالإصدارات السابقة المستخدمة، ولا تستبدلها النسخة الجديدة.

## 7. بوابة اعتماد العقد والتفعيل

يمر كل عنصر بالترتيب التالي:

1. توثيق مسودة العقد وفق القالب.
2. مراجعة الاسم العربي والإنجليزي والمدخلات والمخرجات والأنواع.
3. مراجعة الاعتماديات والصلاحيات والآثار الجانبية.
4. اعتماد المستخدم للعقد.
5. تحديد التغييرات المطلوبة في Lexer/Parser أو Semantic Analyzer أو QIR أو VM أو Web Backend.
6. تنفيذ العنصر في نطاق مستقل مع اختبارات.
7. اجتياز اختبارات الوحدة والرفض والأمان والتوافق والانحدار.
8. تفعيل العنصر بعد تحقق المسار الكامل، لا بمجرد اكتمال التسجيل.

إذا تعذر تنفيذ عنصر دون تغيير مواصفة سابقة، يتوقف التنفيذ ويُعرض التغيير المطلوب لاعتماده منفصلاً.

## 8. النطاق المتبقي لإغلاق المرحلة

تم تنفيذ DATA.ADD وDATA.REMOVE واختبارهما في PR #6. تبقى العناصر التالية قبل إعلان المرحلة السادسة مغلقة:
- تصميم وتنفيذ عقود UI.SHOW وUI.TEXT ومكونات واجهة قابلة لإعادة الاستخدام، مع امتداد QIR منفصل إذا لزم.
- حسم دلالة PROCESS.ADD؛ لا يُستنتج سلوكها من الاسم وحده.
- تصميم عقد INTEGRATION.REQUEST وطبقة موصلات ذات صلاحيات ومصادقة وقيود وجهات آمنة؛ لا يُسمح بفتح شبكة عامة مباشرة من VM أو Web Runtime.
- تحديد حدود شجرة الواجهة وأحداثها وخصائص المكونات وإمكانية الوصول.
- تحديد طبقة موصلات INTEGRATION وآلية موافقات المستخدم والأسرار ومكافحة SSRF وتسرب البيانات.
- سياسة الإصدارات المستقلة للمكونات وتثبيت نسخها في المشاريع.

تُحسم هذه النقاط بمراجعة مستقلة؛ ولا تُحوّل الخيارات المقترحة إلى قرارات ضمنية.

## 9. ما تم وما لم يتم

- تم تنفيذ `DATA.ADD` و`DATA.REMOVE` في Registry وSemantic Analyzer وQIR 1.1 وVM وWeb Runtime، مع اختبارات قبول ناجحة في PR #6.
- بقيت `DATA.GET` معطلة ومؤجلة.
- لم يبدأ تنفيذ UI أو PROCESS.ADD أو INTEGRATION.REQUEST.
- لم تُنشأ موصلات شبكة أو ملفات مضيف؛ تبقى الصلاحيات مغلقة افتراضياً.
- لم يُدمج PR #6 في `main`.

**معيار إغلاق المرحلة السادسة:** إكمال عقود المجموعات الأربع، تنفيذ ما تسمح به المواصفات بأمان، اختبار كل مجموعة وتكاملها، ومراجعة أثر الإصدارات قبل الدمج.
